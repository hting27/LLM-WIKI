# 何時該用（以及不該用）Agent

## 先找最簡單的解法

- 建議先找最簡單的方案，必要時才增加複雜度；這可能代表根本不用做 agentic 系統 [S3]。
- 很多應用只要優化單次 LLM 呼叫（加上檢索與範例）就夠了 [S3]。
- Agentic 系統通常用「更高的延遲與成本」換取「更好的表現」，要確認這個交換值得 [S3]。

## 適合用 agent 的情況

- 開放式問題，很難或不可能預測需要幾步，也無法寫死路徑 [S3]。
- 你對模型的判斷有一定程度的信任，並且能在受信任的環境中運作 [S3]。
- 有清楚的成功標準、能形成回饋迴圈、有人類監督（例如客服、程式碼 agent） [S3]。

## S4 的三個判斷條件

Agent 特別適合「傳統規則式自動化做不好」的工作流程；在決定打造 agent 之前，先確認符合以下條件，否則用確定性的傳統方案就夠了 [S4]：

1. **需要複雜判斷**：有例外、需要看情境決定，例如客服的退款核准。
2. **規則多到難以維護**：規則龐雜、每次修改都很貴又容易出錯，例如供應商資安審查。
3. **大量非結構化資料**：要理解自然語言、從文件抽取意思、和使用者對話，例如處理房屋保險理賠。

S4 的比喻：傳統規則引擎像一張檢查清單；agent 比較像一位有經驗的調查員，會看情境與細微線索 [S4]。

## 什麼時候值得用「多個」agent？

多 agent 系統適合：需要大量平行處理、資訊量超過單一 context、需要操作許多複雜工具，而且任務價值高到值得付出更多 token 成本的情況 [S5]。詳見 [多 Agent 系統](multi-agent-systems.md)。

## 框架的取捨

框架讓起步容易，但多一層抽象會遮住底層的提示與回應，讓除錯更難，也容易誘使人加入不必要的複雜度；建議先直接用 API [S3]。
