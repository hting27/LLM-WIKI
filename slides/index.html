AI Agents
是什麼？

從「會回答的聊天機器人」到「會自己把事情做完的 AI」

本簡報內容全部來自自建的 LLM Wiki（5 篇來源），每頁下方標示依據的 wiki 頁面。按 → 或空白鍵翻頁。

你用過的 ChatGPT，算是 agent 嗎？

單純的聊天機器人、只回答一次的問答、情緒分類器，都有用到 LLM，但 LLM 沒有控制「做事的流程」，所以不算 agent。

聊天機器人

你問一句 → 它答一句 → 結束

它只「說」，不「做」

Agent

你交代一個任務 → 它自己查資料、使用工具、檢查結果 → 把任務完成

它會「做事」，而且自己決定下一步

依據：wiki/concepts/ai-agent-definition.md（S4 的定義與反例）

一句話定義

AI Agent = 會自己決定下一步、會使用工具、在迴圈中把任務完成的 AI 系統。

可以想成一條「把控制權交給 AI 的多寡」光譜：

聊天機器人只回答
Workflow會用工具，但步驟寫死
Agent會用工具，自己決定步驟

不同來源的定義不完全一樣：有的看「有沒有規劃、記憶、工具」（S1），有的看「LLM 有沒有掌控流程」（S3、S4）。共同點是：不只聊天，而是會和外部世界互動。

依據：wiki/concepts/ai-agent-definition.md（綜合 S1、S3、S4 的教學定義）

食譜 vs 廚師

Workflow 像照食譜做菜

每一步要做什麼都寫好了。

✔ 可預測、結果一致

✘ 遇到食譜沒寫的狀況就卡住

Agent 像請廚師「用冰箱裡的東西做晚餐」

他自己看有什麼、決定做什麼、試味道再調整。

✔ 有彈性、能處理意外

✘ 比較貴，錯誤可能一路累積

判斷方法只有一個問題：下一步做什麼，是程式寫死的，還是 AI 自己決定的？

依據：wiki/concepts/workflows-vs-agents.md（S3、S4；比喻為 wiki 中的[整理]）

Agent 由什麼組成？

LLM 是「大腦」，再加上三種能力：

規劃

把大任務拆小，做錯了會反省修正

記憶

記得剛剛做過什麼，也能查外部資料

工具使用

搜尋、算數、查資料庫、寄信……（Tool use）

⚠ 別搞混：另一篇來源（S4）也說「三個核心元件」，但指的是打造 agent 需要的零件：模型、工具、指令。一個講「能力」，一個講「零件」。

依據：wiki/concepts/ai-agent-definition.md、wiki/concepts/augmented-llm.md（S1、S3、S4）

核心：Agent 迴圈

思考：現在該做什麼？

行動：使用工具（搜尋、執行程式……）

觀察：看工具回傳的真實結果，判斷進度

什麼時候停？

  • 任務完成、輸出最終答案
  • 不再需要呼叫任何工具
  • 發生錯誤，或到達最大輪數
  • 遇到卡關，暫停等人回應

依據：wiki/concepts/agent-loop.md（S2、S3、S4）

一個迴圈的實例：ReAct

ReAct 讓模型把「想」和「做」交錯進行。假設任務是「明天出門要不要帶傘？」：

Thought 思考我需要知道明天的天氣。
Action 行動search_weather("台北", "明天")
Observation 觀察天氣服務回傳：明天下午有雨。
Thought 思考會下雨，建議帶傘。→ 給出答案

為什麼有效？只靠腦袋想容易講錯（幻覺），而且一步錯步步錯；先查證再推理就少很多錯。在兩個互動任務中，成功率分別絕對提升 34% 與 10%。

依據：wiki/concepts/react.md（S2）

規劃：先拆解，做錯再反省

任務拆解

Chain of Thought：「一步一步想」，把難題拆成小步驟。

Tree of Thoughts：每一步想好幾種可能，再挑最好的路。

自我反思

失敗後寫下「哪裡做錯、下次怎麼改」，放進記憶，下次參考（例如 Reflexion）。

真實世界的任務很少一次就成功，所以這很重要。

依據：wiki/concepts/planning.md（S1）

記憶：短期 vs 長期

人類Agent
短期記憶同時只能記住少量東西模型一次能「看到」的文字範圍（context window），有長度上限
長期記憶可以保存很久外部資料庫，需要時再查出來

實務作法：重要的東西要寫到外部。例如一個研究 agent 會先把研究計畫存起來，因為內容超過 200,000 個 token 時，舊的部分會被截掉。

依據：wiki/concepts/memory.md（S1、S5）

工具：Agent 的手和腳

類型做什麼例子
資料拿到需要的資訊搜尋網路、讀 PDF、查資料庫
行動對外部系統做事寄信、更新紀錄、轉給真人客服
編排呼叫其他 agent研究 agent、寫作 agent

工具說明要寫得讓 AI 看得懂（稱為 ACI）。例：一個寫程式的 agent 常把相對路徑弄錯，改成只接受絕對路徑後就不再出錯；另一個團隊改寫工具說明後，任務完成時間少了 40%。

依據：wiki/concepts/tool-use.md（S3、S4、S5）

五種常見的組合方式

模式白話說明例子
提示鏈固定步驟，一棒接一棒寫大綱 → 檢查 → 寫全文
路由先分類，再交給專門流程客服問題分流
平行化同時做好幾件事，或同一件事做好幾次投票多個角度同時審查程式碼
指揮者-工人一個 orchestrator 臨機拆工作、分派、整合修改多個檔案的程式任務
評估者-優化者一個寫、一個評，來回改到好文學翻譯

它們是積木，可以自由組合；但只有在確定效果更好時才增加複雜度。

依據：wiki/concepts/workflow-patterns.md（S3、S5）

一個不夠，那就多個？

一個主 agent 擬定研究計畫，同時派出好幾個子 agent 分頭搜尋，最後整合成報告。

90.2%在研究任務上，多 agent 比單一 agent 表現更好
15 倍多 agent 系統用掉的 token 約是一般聊天的 15 倍（單一 agent 約 4 倍）
不適合大家必須共享同一份資訊、彼此高度相依的任務（例如多數寫程式的工作）

所以一般建議是：先把一個 agent 做好，真的需要平行處理大量資訊、而且值得付出成本時，才用多個。

依據：wiki/concepts/multi-agent-systems.md（S4、S5，含「觀點差異」）

什麼時候該用 agent？

第一原則：能簡單就簡單。很多問題只要把一次提問寫好就夠了；agent 用「更慢、更貴」換「更好的表現」。

值得用 agent 的三種情況

  1. 需要判斷：有很多例外，要看情境決定（例：客服退款核准）
  2. 規則多到難維護：每次改規則都又貴又容易出錯（例：供應商資安審查）
  3. 大量文字資料：要讀懂文件、和人對話（例：處理保險理賠）

比喻：規則引擎像一張檢查清單；agent 像一位有經驗的調查員。

依據：wiki/concepts/when-to-use-agents.md（S3、S4）

風險與防護欄

主要風險

  • 錯誤會累積：一步走錯，後面全走偏
  • 可能講出看似合理但錯誤的內容
  • 成本高、結果每次不一定相同
  • 有人在輸入裡偷藏指令（prompt injection）

防護方式

多層 guardrail：過濾離題與危險輸入、保護個資、把工具依風險分級。

兩種時候一定要交給人：

  1. 重試多次仍然失敗
  2. 高風險、不可逆的動作（取消訂單、大額退款、付款）

依據：wiki/concepts/challenges-and-risks.md、wiki/concepts/guardrails-human-oversight.md（S2、S3、S4、S5）

怎麼知道 agent 做得好不好？

同一個任務，agent 每次走的路可能都不同，所以要看結果對不對、過程合不合理，而不是有沒有照固定步驟走。

馬上用小樣本測

約 20 個真實問題就能看出改動有沒有用

讓 AI 當評審

LLM-as-judge：依事實、引用、完整性、來源品質、工具效率打分

人一定要看

例：人發現 agent 偏好品質差的農場文，而不是學術 PDF

注意：在需要深度專業的領域，AI 評審可能看不出錯誤，所以不能只靠它。

依據：wiki/concepts/evaluation.md（S1、S5）

小測驗

1. 一個情緒分類器（判斷評論是正面或負面）算 agent 嗎？

不算。它有用到 LLM，但 LLM 沒有控制做事的流程，也沒有使用工具完成任務。

2. Agent 迴圈的三個步驟是什麼？

思考 → 行動 → 觀察，然後根據觀察結果再思考，直到任務完成或到達停止條件。

3. 每週把固定格式的報表從 A 系統複製到 B 系統，適合用 agent 嗎？

通常不需要。步驟固定、不需要判斷，用寫好的程式（或 workflow）就夠了；能簡單就簡單。
